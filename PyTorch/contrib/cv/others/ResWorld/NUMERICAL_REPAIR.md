# ResWorld 数值问题：根因、实际修复与验证

## 1. 当前结论

2026-10-18在7.6.28.252实际修复并复验。原156参数失败和后续1参数失败均已解决；五份固定权重各446个有效梯度全部通过原门槛。四卡严格恢复、持续训练、独立重载及作者65帧评测也分别完成。原失败记录完整保留，正式nuScenes trainval/12epoch与驾驶业务精度另行验收。

## 2. GELU计算语义

固定镜像中普通NPU `F.gelu(x, approximate='none')` 实测接近tanh近似。真实捕获输入与CPU erf定义最大差约4.73e-4；官方 `torch_npu.npu_gelu(x, approximate='none')` 约4.77e-7。

仅绑定原三个GELU的NPU路径，使用官方原生前后向；CPU默认erf保持。仅这一项修复后整网仍约2.6149%误差，未将它当成唯一原因。

定义依据：[PyTorch2.7.1 GELU](https://github.com/pytorch/pytorch/blob/v2.7.1/torch/nn/modules/activation.py#L654)、[华为npu_gelu接口及原生gelu语义说明](https://www.hiascend.com/document/detail/en/Pytorch/2610/apiref/customapi/docs/en/custom_APIs/torch_npu/torch_npu-npu_gelu.md)。官方当前文档明确说明原生NPU gelu默认使用tanh，指定erf应调用npu_gelu。数值来自本项目固定镜像实测，不外推到其他版本。

## 3. 时序残差的FP32相消

原 `S @ F0 - S @ F1` 先执行两次长归约再相减，损失小残差的有效数字；归一化和ReLU会放大反向差异。改为等价 `S @ (F0-F1)`，保留重复位置编码及零导数连接。CPU和NPU都采用稳定顺序。

CPU参考浮点顺序因此改变，另以真实捕获特征/CAN、原两个规划loss、**未修改原公式CPU FP64规划头**建立独立标杆：旧CPU FP32梯度相对L2为0.028733437761987904；稳定CPU FP32为1.1745830156671147e-5，NPU相同CPU特征为9.332136131187707e-6，NPU实际特征为0.0004887004536854625，三个稳定路径均无越界参数。该标杆覆盖规划头及其输入梯度。

原bf7a权重和dccd真实批次保持不变。初始446梯度中156个越界、整体relativeL2=0.026409216870826344；最终三项配置该病例446个全部通过，relativeL2=0.000542465076158。

## 4. 常量几何投影的后端舍入

前两处修复后，新训练07a6权重仍1参数越界。CNN中极少近零ReLU分支不同传播到该梯度。相同真实输入和上游梯度下，原生NPU卷积权重反向对FP64最大差约7.29e-8；完整BEV分支反事实解释差范数约99.8%。捕获mask只用于诊断，未部署。

最终保留原 `RCSample.get_sample_coor` 方法和原FP32归一化运算，把固定BEV坐标、标定及增强矩阵统一在CPU计算，再将网格送回NPU。任何可学习元数据直接拒绝。NN特征、采样、loss和反向仍在NPU。

## 5. 新配置独立回归

五份固定权重为原bf7a、后续07a6、旧长稳72afe、新配置新20步、最终长稳权重。每份都使用同权、同真实批次和原阈值，分别保存完整逐参数JSON。

新四卡10+10恢复与连续20：2054/2054完整状态张量逐位相同、最大差0，全部rank实际增强输入一致。新配置四卡持续训练1811.967955秒、660次更新；最终梯度446个全部通过，relativeL2=2.83294570892e-05，独立重载通过。作者完整权重原65帧CPU/NPU轨迹及逐帧原离散碰撞值对照通过。

## 6. 未采用的尝试

- GELU单独、仅NPU稳定残差对旧CPU参考，均未完整通过。
- must_keep_origin_dtype/high_precision和内部格式未消除残留，未采用。
- 旧JIT出现tiling越界和不可信输出提示，停止并拒绝采用。
- 补偿卷积虽改善单算子误差，整网仍失败；几何CPU FP64仍有3个参数越界，均未采用。
- 全网CPU FP64明显改变原深度损失，且目标参数仍越界；没有以它替换原FP32验收。
